ThreatScope meeting/demo instructions

Goal of the meeting:
Show that ThreatScope works end to end and explain what each person owns.

Simple project summary:
ThreatScope is a real-time Network Intrusion Detection System.

The flow is:
network/demo packets -> Python Scapy engine -> FastAPI API -> Supabase -> React dashboard

The engine detects:
- PORT_SCAN
- SYN_FLOOD
- PING_SWEEP
- ARP_SPOOF

What the four detections mean:
- PING_SWEEP: one source pings multiple IP addresses to find live hosts on a network. This is early reconnaissance. Severity: LOW.
- PORT_SCAN: one source checks many ports to find open services. This is stronger reconnaissance and often comes before an attack. Severity: MEDIUM.
- ARP_SPOOF: one device claims another device's IP address on the local network. This can be used for man-in-the-middle attacks. Severity: MEDIUM.
- SYN_FLOOD: one source sends many TCP SYN packets to overwhelm a target service. This is an active denial-of-service pattern. Severity: HIGH.

Why only these four for the demo:
ThreatScope is an MVP, not a full Snort or Suricata replacement. We chose four rules because they are common, easy to explain, testable in a short demo, and show different stages of suspicious activity:
- discovery: PING_SWEEP
- service reconnaissance: PORT_SCAN
- local network attack setup: ARP_SPOOF
- active disruption: SYN_FLOOD

Honest framing:
"ThreatScope currently detects a focused set of common network behaviors in real time. The rule engine is intentionally small for the MVP so we can prove the full pipeline works end to end: packet analysis, API ingestion, Supabase storage, realtime updates, and dashboard visibility. More detections can be added later using the same pattern."

Ollama / AI framing:
"Ollama is used locally as a developer diagnostic helper. It reads recent alerts after the rule engine has already detected them, then summarizes the pattern and suggests possible rule tuning. It does not replace the detection rules and it is not a public chatbot."

Cloud AI framing:
"The AI layer can also be switched to a cloud provider with an API key. That makes the analysis feature work without relying on one teammate's local machine, while the detection rules still remain the source of truth."

Scheduled scan framing:
"The dashboard can start a scan now or schedule scan windows every 5 or 10 minutes. When a scan starts, the dashboard tells the user ThreatScope is checking the network. If no new alerts appear during that scan window, it reports Network is secure."

Terminal 1: Start the API

cd api
source ../.venv/bin/activate
uvicorn main:app --reload --host 0.0.0.0 --port 8000

If that venv does not work:

cd api
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn main:app --reload --host 0.0.0.0 --port 8000

Optional API health check:

curl http://localhost:8000/health

Expected result:

{"status":"ok","service":"ThreatScope API"}

cd dashboard
npm install
npm run dev

Open this in the browser:

http://localhost:5173

What Cristian says:

Optional Ollama setup:

Install Ollama:
https://ollama.com/download

Pull the recommended local model:

ollama pull qwen2.5:7b

Optional lighter model:

ollama pull llama3.2:3b

Required .env values:

AI_PROVIDER=ollama
OLLAMA_BASE_URL=http://127.0.0.1:11434
OLLAMA_MODEL=qwen2.5:7b
OLLAMA_TIMEOUT_SECONDS=45
OLLAMA_ALERT_LIMIT=20

For a clean demo AI summary, either clear older test alerts before presenting or temporarily set:

OLLAMA_ALERT_LIMIT=4

This keeps Ollama focused on the four current demo alerts instead of older test/simulated rows.

Optional cloud AI values:

AI_PROVIDER=openai
OPENAI_API_KEY=your-api-key
OPENAI_MODEL=gpt-4o-mini
OPENAI_BASE_URL=https://api.openai.com/v1
